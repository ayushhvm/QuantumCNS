# Technical Report: Post-Quantum Secure Messaging Application

## Executive Summary
This project is a **Post-Quantum Secure Messaging Web Application** developed as a semester lab project for an Information Security Engineering (ISE) course. It acts as a proof-of-concept for transitioning modern communication systems toward post-quantum cryptography. 

Unlike traditional secure chat apps that rely entirely on classical algorithms (like RSA or Elliptic Curve Cryptography) which are vulnerable to future quantum computers running Shor's algorithm, this application uses a **hybrid cryptographic handshake**. It secures symmetric session keys using both classical and post-quantum methods simultaneously, ensuring that even if one mechanism is compromised, the session remains secure.

---

## 1. Cryptographic Architecture

The core innovation of this project lies in its cryptographic stack. By combining two distinct key-exchange paradigms, it achieves robust, quantum-resistant forward secrecy.

### 1.1 The Hybrid Handshake
The key exchange mechanism relies on two parallel processes:
1. **Classical Key Exchange (ECDHE):**
   - Uses **Elliptic Curve Diffie-Hellman Ephemeral (ECDHE)** on the NIST standard `secp256r1` (P-256) curve.
   - Operated via the Python `cryptography` library.
   - Provides standard, time-tested security against classical computers.
2. **Post-Quantum Key Exchange (Kyber):**
   - Uses the **CRYSTALS-Kyber Key Encapsulation Mechanism (KEM)**, specifically the `Kyber512` parameter set. 
   - Kyber is based on the "Module Learning with Errors" (ML-LWE) mathematical problem. It has been officially standardized by NIST as FIPS 203 (ML-KEM).
   - Implemented using the `liboqs` (Open Quantum Safe) C-library under the hood, accessed via the `liboqs-python` wrapper backend and `liboqs-wasm` in the frontend.

### 1.2 Key Derivation (KDF)
The shared secrets generated by ECDHE and Kyber are independent. To unify them into a single usable key, the application uses an **HMAC-based Key Derivation Function (HKDF)** with SHA-256. 
- The inputs are concatenated: `ikm = kyber_secret + ecdhe_secret`.
- The HKDF securely expands this material into a highly entropic **256-bit (32 bytes)** symmetric session key.

### 1.3 Message Encryption
Once the AES-256 session key is derived, the actual payload of the chat message is encrypted using **AES-GCM (Advanced Encryption Standard in Galois/Counter Mode)**.
- GCM provides *authenticated encryption*. It guarantees **confidentiality** (the message cannot be read) and **integrity** (a tag ensures the ciphertext hasn't been intercepted and tampered with in transit).

## 2. Software Architecture

The project is structured into three distinct layers:

### 2.1 Backend Server (`app.py` & Flask)
- Built on **Flask** and **Flask-SocketIO**.
- Handles standard HTTP requests for loading the frontend GUI (`GET /login`, `GET /chat`).
- Manages an in-memory session and user identity store (`auth/users.py`), providing authentication tokens.

### 2.2 The Socket.IO Relay Logic
The server operates not just as a routing mechanism, but as an active participant in establishing secure endpoints.
- **Client-to-Server Encryption:** The application does *not* utilize pure End-to-End Encryption (E2EE) between Alice and Bob. Instead, it utilizes client-to-server TLS-like sessions. 
- During a `handshake_init` event, the server acts as the peer. It dynamically generates its own Kyber and ECDHE keypairs, computes the shared parameters, and issues the handshake response back to the client.
- When `send_message` triggers, the server decrypts the message using the sender's AES key, immediately re-encrypts the payload using the recipient's AES key, and forwards it to the correct socket.

### 2.3 Frontend Client (`static/js/crypto_client.js`)
- The browser must independently perform its half of the complex key exchange.
- It leverages the standard WebCrypto API for standard functions (AES-GCM and ECDHE).
- It dynamically loads a WebAssembly (WASM) build of liboqs (`liboqs-wasm`) to perform the heavy lattice-based Kyber cryptography directly in the client's browser.

## 3. The User Journey & Data Flow

1. **Authentication:** A user (e.g., Alice) visits `/login`. They input their credentials, the server hashes the password against its store, and returns a 32-byte hexadecimal authentication token.
2. **WebSocket Connection:** Alice is redirected to `/chat`. The browser establishes a Socket.IO connection presenting the token. 
3. **The Handshake:** 
   - Alice's browser generates Kyber and ECDHE public keys and sends them to the server.
   - The server catches them, generates its pair, completes the encapsulation/math, and sends its public keys/ciphertext back.
   - Both Alice's browser and the server run their KDF math independently, arriving at the exact same AES-256 session key.
4. **Chatting:** 
   - Alice types a message and clicks send. The browser encrypts it with AES-GCM. 
   - A packet consisting solely of `{nonce, ciphertext, tag}` is sent over the wire.
   - The server validates the tag, decrypts it, re-encrypts it for the intended recipient (Bob), and transmits it. 
   - Bob's browser catches the new ciphertext, runs AES-GCM decryption, and prints the plaintext to the screen.

---

## 4. Conclusion & Academic Value
As a university lab project, this codebase is exceptionally well-structured to demonstrate the mechanics of moving beyond classical RSA/ECC cryptography. By surfacing a "Crypto Terminal Panel" in the frontend GUI that logs the raw cryptographic steps in real-time, it acts as both a secure application and an educational visualizer for the incoming NIST ML-KEM standards.
